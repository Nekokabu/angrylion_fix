# ドンキーコング64 タイトルデモ デシンクの原因解析と ares への修正

対象ROM: Donkey Kong 64 (J) ― NDOJ, CRC 053C89A7-A5064302, big-endian 32MB
対象エミュレータ: ares (master 9408cb43 で開発、a774671d 2026-10-26 時点の master にも適用可)
更新: 2026-10-31（実機テスト ROM v9〜v16 の結果を反映。VI モード係数・動的バス競合・CPU 命令タイミング・SP DMA を実測値に）

## 結論（要約）

- デシンクの原因は **描画タイミングではなく「ゲームが計測するフレーム間隔（VIリトレース数 = フレームデルタ）」の系列の違い** です。
- DK64 の DKTV デモは「ゲームフレームごとに記録した入力（スティックX/Y・ボタン・カメラ角）」を再生し、キャラの移動量は **デルタ（2=30fps, 3=20fps …）倍** にスケールされます。
- 実機ではジャングルジャペスのこのデモは **常時デルタ3（1フレームが2VI=33.3msを確実に超える）** で動きます。
  これは DK64 Recompiled プロジェクトが同じ場面でデルタを3に固定して直していることからも裏付けられます
  (`patches/patches_main.c`: `if (gameIsInDKTVMode() && current_map == MAP_JAPES) D_global_asm_80744478 = 3;`)。
- ares は RDP の実行時間が **0** で、フレーム時間が CPU 時間だけで決まり、ちょうど 33ms 前後で揺れるため
  **デルタが 2 と 3 を行き来** します。入力はフレーム単位なので、デルタ2のフレームでは DK の移動量が 2/3 になり、
  ヤシの木の反対側を通ったりロープに届かずに落下します。
- 修正として ares の RDP に **コマンド列からの実行時間見積りモデル** を追加し、Sync_Full の DP 割り込みと
  DPC_STATUS の busy フラグをその分だけ遅延させるようにしました。モデルの係数は **実機（N64Digital HDMI 出力を
  EzRecorder 330 で 60fps 録画）のフレーム表示間隔**と突き合わせて較正しています。修正後は電源投入からの通し実行で、
  崖を登り→ロープに飛び移り→振り子で対岸へ→たる大砲で射出、と実機どおりに完走します。
- 2026-10-27 更新: 実機テスト ROM（v7/v8）の計測結果で、推定だった補正係数を **計測値（配置ペナルティ・モード別競合・VI）**に置き換え、
  RDP 描画中の CPU キャッシュ転送の遅れ（計測値）を `0003` として追加しました。
- 2026-10-31 更新（パッチ 0004〜0007）: ゲームのディスプレイリストそのものを実機で再生する ROM（v9/v10/v12/v15）と、
  CPU（v11/v14）・RSP（v16）の命令タイミング ROM の結果で、モデルの残りの自由度をすべて実測値に置き換えました。
  **VI モードの係数**（ゲームの AA+divot+dedither モードで RDP +11.7%、hires +32%、MGC の aa2 モードで +3%）、
  **バスマスターごとの動的競合**（CPU フィル 11.7 / 命令フィル 8.5 / ライトバック 5 / SP DMA 1.22 clk/8B）、
  配置ペナルティ 15、CPU 側は FPU（パイプライン化、div/sqrt 29〜30、cvt 5）・ロード/ストアのハザード・
  リコンパイラの二重課金修正・非キャッシュ読み 32 / RCP レジスタ読み 23、SP DMA 38 cycle + 0.155/B。
  DK64 デモは過去最良（スコア 22）、BAR のクラッシュシーンは一致、BAR の intro は 2.0 vs 実機 2.5 VI/フレームの
  ナイフエッジが残ります（下記）。
- 2026-11-01 追記（bar_tasklog）: ゲーム本体に常駐ロガーを入れるパッチで BAR intro の全フレームを実機で記録し（通常版と CPU を止めた版）、
  残差を分解。CPU 競合はモデルの 8% 内、RSP/RDP は CPU 停止でも実機が +2.7%（重）/ +6.7%（軽）。v15 の種別別解析で、クラッシュ場面の
  −7% は **Z テスト通過率**（場面の描画順に依存）と判明。一律係数では DK64 と両立しないため series v7 のまま（パッチは v7 と同一）。
- 2026-10-31 追記（series v7、パッチ 0011）: v20 の各条件を「大きな FIFO（RSP が待たない）」「RDP 凍結 → RSP 単独 / 解凍 → RDP 単独」に分解する
  ROM（v20b）で、ares の **RSP 単独（F3DEX2）は実機 +2%、RDP 単独は −1%**（フレーム 2316）と確認。足りなかったのは **RSP の DMA が RDP から
  奪う時間**（実機 0.057 VI/フレーム、VI ゲームモードで 0.080、ares は 0.049）で、DMA 1 回の基本コスト 6 → 9 と VI 係数の適用で補正。同じ ROM の
  CPU チェイスから CPU フィル 1 回の RDP 損失を 11.7 → 10（VI オンで 13.3）に再計測。RDRAM ページ効果の ROM（v21）は CPU 側に変更不要と判定。
  BAR intro 252 → 249 フレーム（実機 225）、DK64 は変わらず。
- 2026-10-31 追記（series v6、パッチ 0010）: ゲームの RSP グラフィックタスクを実機で再生する ROM（v20）で、**実機では RSP のタスクが RDP の
  0.05〜0.3 VI 手前まで FIFO 満杯で待つ**（ares は 3 倍早く終わっていた）ことが判明。`DPC_CURRENT` をモデルの進捗に従って返す修正で
  RSP が実機どおりに待つようになり、BAR intro は 271 → 252 フレーム（実機 225）、60 VI ごとのフレーム数の形が実機と一致。
- 2026-10-31 追記（パッチ 0007〜0009、series v4）: `0007` は MGC 2011 デモのエミュレータ検出を通す PI タイミング修正に差し替え。
  複合負荷 ROM（v17）、CPU 第 3 弾（v18）、SP DMA 競合 ROM（v19/v19b）の結果を `0008`/`0009` として追加: FPU は通常オペランドで
  add 3 / mul.s 5 / mul.d 8 / div.d・sqrt.d 58（v14 の「2 / 30」は高速パス）、4 エントリのライトバッファ（非キャッシュ書き 16 cycle/個、
  フィル・非キャッシュ読みは排出待ち）、ダーティ書き戻しの非同期化、cache 命令 5、非キャッシュ書きの RDP ペナルティ 4、
  SP DMA の VI ×1.12 と CPU ライン転送との相互遅延、DMA 連続中に RDP が DMA 1 回あたり 36 clk しか使えない規則（v19b）。負荷の相互作用は足し算で超加算なし。BAR intro は変わらず（残課題参照）。

## 解析の経緯

### 1. ゲーム側の仕組み（ROM 解析）

J版の本体コード（global_asm）は ROM 0x116F0 の gzip を RAM 0x805F8B00 へ展開したものです。

| 項目 | J版アドレス | 内容 |
|---|---|---|
| VI割り込みハンドラ | 0x8060CCA4 | VIリトレース数 (`sched+0x284` = 0x80767EB4) を加算、保留中のバッファスワップを実行 |
| RDP完了(DP割り込み)ハンドラ | 0x8060D1A4 | `D_807460D0`(次スワップ許可VI) と比較してスワップ or 保留。スワップ後 `osDpSetStatus(FREEZE)` |
| フレームデルタ算出 | 0x805FE024 | `t0 = リトレース数 − 前回` を8要素履歴に記録し、ヒステリシス付きで `D_80743D38`(デルタ)を更新。その後 `リトレース ≥ 前回+デルタ` までビジーウェイト |
| DKTV入力再生 | 0x80608EC4 / 0x80608F4C | エントリ(4バイト: 15bitカメラ角+ボタン更新フラグ, スティックX, スティックY) をゲームフレームごとに1つ進めてパッド構造体 (0x807ED180) に書き込む |
| 物理のデルタ消費 | 0x8061B7E4 ほか多数 | `delta × 0.5` を時間ステップとして使用（デルタ2で1.0, 3で1.5） |

ヒステリシスの規則: 直近2フレームの t0 が現在のデルタより大きければ即座に上げる／直近4フレームすべてが小さければ下げる。
したがって **厳密なサイクル一致は不要**で、「フレーム時間が常に33msを超えているか」だけでデルタ系列が決まります。

### 2. ares での再現と検証（ヘッドレスハーネス）

GUI 依存を外した自作ハーネスで ROM を走らせ、RAM（現在マップ 0x8076A298、プレイヤー座標 ptr 0x807FBFBC +0x7C/0x80/0x84、デルタ 0x80743D38、DKTVインデックス 0x80745C6C）を毎VIフレーム記録しました。

| 条件 | デルタ系列（デモ中） | 結果 |
|---|---|---|
| ares 現状（RDP時間0） | 3が主体だが 2 が頻繁に混入 (2×15, 2×22, 2×27 …) | X≈1758 で谷へ落下（報告どおり） |
| デルタを 2 に固定（コードをRAM上でパッチ） | 常に2 | 別経路で落下 |
| **デルタを 3 に固定** | 常に3 | **ロープに飛び移り振り子で対岸へ→たる大砲で射出→次のデモへ遷移（正常）** |
| 修正版 ares（既定値） | ほぼ3（開始直後に4が少し、後半に短い2） | **正常に完走** |

デルタ3固定で正常になることが、原因がフレームデルタ系列であることの直接証明です。

また RDP 時間とは独立に、ares では CPU がデモ中ほぼ100%ビジー（アイドルスレッド 0x80000A04 のPCサンプルは約2.5%）で、
1ゲームフレームあたり dcache ミス約3万回（≈13ms）＋ライトバック約1万回（≈4ms）とキャッシュミス支配的でした。
実機では RDP が RDRAM を占有する間 CPU のキャッシュフィルも遅くなるため、CPU 側も ares より遅いはずです。

### 3. 既知情報との整合

- ares Issue [#1652](https://github.com/ares-emulator/ares/issues/1652) / [#1175](https://github.com/ares-emulator/ares/issues/1175): 原因未特定、「タイミングに非常に敏感」とのみ。
- simple64 の 2022.07 リリースノート「DK64 イントロでロープを掴むようになった」はタイミング全般の見直しによるもの。
- [DK64 Recompiled](https://github.com/Rainchus/Donkey-Kong-64-Recompiled) の `patches_main.c` はジャペスの DKTV でデルタを 3 に固定（本解析の結論と一致）。
- ares の「10回に2回成功」（PAL）は、ares が RDRAM 初期化タイミングを乱数化している（`rdram.cpp` の ccLow/ccHigh）ため起動時刻がずれ、
  境界付近のフレームがたまたま 3 側に倒れた場合と考えられます。

### 4. 実機録画による較正

実機の録画 2 本（1080p 59.94fps）から、連続する同一フレームの数（＝表示間隔のVI数）を抽出しました
（`analyze.py`: 480×270 グレースケールの平均差分 > 0.6 で「絵が変わった」と判定）。2 本の録画はデモ区間全体で
25フレームブロックごとの合計が ±1VI 以内に一致し、**実機の挙動は決定的**です。

ジャペスのデモ区間（約494ゲームフレーム）について、25ゲームフレームごとのVI数合計（実機 → ares）:

| ブロック | 0 | 25 | 50 | 75 | 100 | 125 | 150 | 175 | 200 | 225 | 250 | 275 | 300 | 325 | 350 | 375 | 400 | 425 | 450 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 実機 | 79 | 75 | 76 | 78 | 83 | 82 | 78 | 75 | 75 | 74 | 71 | 73 | 75 | 80 | 77 | 75 | 74 | 70 | 73 |
| ares 修正前 | 97 | 74 | 73 | 80 | 87 | 88 | 83 | 76 | 71 | **65** | **64** | 72 | **63** | **64** | 73 | 77 | 72 | 74 | 72 |
| ares 修正後 | 98 | 77 | 76 | 80 | 86 | 87 | 84 | 77 | 76 | 75 | 75 | 76 | 79 | 87 | 76 | 77 | 75 | 75 | 69 |

表示間隔のヒストグラム（2/3/4以上）: 実機 28/436/30、修正前 105/319/76、修正後 19/417/64。

- 修正前の ares は前半（CPU律速の区間）では実機にほぼ一致〜数%遅い一方、後半（実機では RDP 時間が CPU を上回る区間）
  で 2 が多発し（ブロック合計 63〜65 = 平均 2.6VI）、ここでゲームのデルタが 2 に落ちてデシンクしていました。
- 当初検討した「RDP ビジー中の CPU キャッシュフィルにペナルティを課す」案は、前半の CPU 律速区間を実機より大きく
  遅くしてしまう（ブロック合計 92〜104）ことが録画との比較で判明したため、この時点では採用しませんでした
  （当時の値は一律 12〜20 サイクル。後に実機で計測した値 10/4/12 を `0003` として採用、2026-10-27 の節を参照）。
- RDRAM 競合係数は 2.5 だと後半が速すぎて失敗、3.5 だと遅すぎて失敗、2.6〜3.0 で完走（2.75〜2.9 で誤差最小）。
  後述のビートルアドベンチャーレーシングとの両立で **2.9** を採用（推定モデル時点の値。実機計測モデル組み込み後は係数の意味が変わり **1.8**、後述）。

## ビートルアドベンチャーレーシング (J) の OP デモ（推定モデル時点の較正）

同じ手法で実機録画（2本、こちらも±数VIで一致＝決定的）と ares を比較しました。

- OP は 30fps 基調（表示間隔2）で、軽い場面では 60fps 寄り（1 2 1 2…）、重い場面では 33ms 超（2 3 2 3…）。
  シーンカットは時間基準（各シーンの VI 数は ares と実機で一致）ですが、シーン内のゲームフレーム数は
  エミュレータのフレーム時間で変わります。
- 修正前の ares（RDP 時間 0）は OP 全体が 60fps。係数 3.0 では重いシーンで実機より約25%遅く
  （例: seg1 実機306フレーム vs ares 281）、2.75 でシーンごとのフレーム数が最も近づきます。
- ヘリ衝突シーン（セグメント開始からの VI 数、実機: 分解開始 +658〜660、「クラッシュ」表示 +668）:

| 係数 | 分解 | 文字 | 間隔 |
|---|---|---|---|
| 実機 | +658〜660 | +668 | 8〜10 |
| 2.6 | +644 | +666 | 22 |
| 2.75 | +652 | +664 | 12 |
| **2.9** | **+658** | **+668** | **10** |
| 3.0 | +662 | +672 | 10 |

  分解（車の進行＝フレーム基準）と文字（時間基準）の相対タイミングが係数で動き、2.9 で実機と一致します。
- 「文字が先に出る」症状は、最初に送ったパッチ（係数2.5＋CPU ストール12）で起きるものです。CPU ストール項は
  CPU 律速の軽い場面を実機より遅くするため、車の進行が遅れて文字が先行します。現行版（CPU ストールなし）では
  headless 環境で再現せず、順序・間隔とも実機どおりです。
- 検証スクリプト: `seq.py`（ares の描画統計から表示間隔列）、`cmpseg.py`（実機動画とシーン単位で比較）。

## 実機計測 RDP タイミングモデルの組み込み（2026-10-26 更新）

別セッションで計測した `rdp_timing_model`（v3〜v6、NTSC/PAL 同一、中央値誤差 0.5%）を、当初の
「理想値 × 競合係数 2.9」の推定モデルと**置き換え**ました。推定モデルとの主な違い:

| 項目 | 旧（推定） | 新（計測テーブル） |
|---|---|---|
| スパン | 画素レート + ストリーム毎 (2.5+6+B/8)×2.9 + 12 | モード×アドレス位相×幅のテーブル（RDRAM 待ち込み） |
| 1cyc16 320px | 589 clk | 331 clk（ほぼ画素レート律速） |
| 1cyc16 blend+Z 32px | 235 clk | 170 clk（×1.8 で 280） |
| fill16 320px | 331 clk | 192 clk（×1.8 で 282） |
| プリミティブ | 14 固定 | モード・幅依存（−15〜+35、連続描画でオーバーラップ） |
| ロード | 8B/clk + RDRAM 読出×2.9 | 13.5 + 0.48/word + 22.7/64B 等の計測式 |
| Z フェイル | 区別なし | 別テーブル（パスの約半分）、オーバードローからパス率推定 |

テーブルを**そのまま**（競合係数 1.0）使うと DK64 は後半が速すぎて失敗します（実機では CPU/RSP/VI が RDRAM を取り合うため）。
RDRAM 待ち部分にだけ係数を掛ける形で再較正した結果:

| 係数 | DK64 誤差(25fr ブロック合計差) | DK64 2/3/4 ヒスト | DK64 完走 | BAR seg0/seg1 フレーム数（実機 225/306） | BAR 衝突 分解/文字（実機 +658〜660/+668） |
|---|---|---|---|---|---|
| 1.0 | 72 | 91/333/76 | ✗ | – | – |
| 1.5 | 53 | 52/382/66 | ✗ | – | – |
| 1.7 | 39 | 36/408/56 | ○ | 278/347 | +629/+667 |
| **1.8** | **38** | 30/410/60 | ○ | 251/327 | +639/+667 |
| 1.9 | 42〜46 | 31/412/57 | ○ | 251〜253/313〜331 | +638〜644/+666 |
| 2.0 | 66 | 17/404/79 | ○（ブロック13が95＝デルタ4混入） | – | – |
| 旧モデル 2.9 | 40 | 25/419/56 | ○ | 257/302 | +658/+668 |

- DK64 は 1.8 で旧モデルと同等以上（ヒストグラムも実機 28/436/30 に最も近い）。1.6〜1.9 で完走。
- BAR は新モデルの方が実機より **3〜7% 速い**側に残ります（重い場面で 2VI フレームが多く、衝突の分解が実機より約 20VI 早い。
  文字は時間基準なので一致）。BAR だけなら係数 2.3〜2.4 が最良ですが DK64 が 2.0 で失敗するため両立しません。
  「文字が分解より先に出る」症状は出ません（分解 +639 → 文字 +667）。
- 両者を分ける要因を調べましたが決め手は見つかっていません:
  - CPU/RSP の RDRAM トラフィック（ares の RBus 統計）は両ゲームとも約 32MB/s で同じ → 可変係数では説明できない。
  - VI 設定（320×240 16bit、AA+divot）も同一。
  - RSP が RDP の出力バッファ消費を待つ（DPC_CURRENT スロットリング）モデルを試したところ、DK64 だけが大きく遅くなり
    BAR は変化なし → 採用せず（BAR は DP 完了待ち、DK64 は SP 完了に反応するゲームループと推測）。
  - 両ゲームのバッファ配置（ares で取得）: BAR は色 0x1DA800 / 0x200000、Z 0x3DA800（片方の色バッファと Z がちょうど 2MiB 差＝
    下位アドレスが同一）、DK64 は色 0x01D240 / 0x042A40、Z 0x5D2E00（拡張パック領域）。
  - 切り分け用の実機テスト ROM `rdp_timing_v7`（libdragon、SD 保存、4MiB 機で動作）を `rdp_timing_v7.zip` に用意
    （A: 色/Z バッファ配置、B: プリミティブ間の set/sync コマンド、C: 小プリミティブ間のテクスチャロード、
    D: CPU/SP DMA/VI による RDRAM 競合の直接計測、E: 散在プリミティブ）。結果は `analyze_v7.py` で集計できます。
  - 残る候補は色／Z バッファのバンク競合（計測は両バッファをページ境界に配置。BAR のバッファ配置で行ミスが増える可能性）、
    Set_Other_Modes を Sync_Pipe なしに多用（BAR はフレームあたり 704 回）した際の暗黙のパイプライン待ち、
    BAR 側の CPU 時間の誤差。これらは追加の実機計測（バッファアドレスを変えたスパン計測、set 系連続時のコスト）で切り分けられます。
- `zPassAuto=false` にして `zPassFraction` を固定することもできます（固定 0.75 では DK64 がやや速く、BAR はさらに速くなります）。

## 実機テスト ROM v7/v8 の結果と最終モデル（2026-10-27 更新）

前節の「両者を分ける要因」を切り分けるために作った実機テスト ROM（`rdp_timing_v7` / `rdp_timing_v8`、libdragon、
SD 保存）の NTSC/PAL 実機の結果（`hw/` に原本、NTSC と PAL は全系列で一致）です。

### RDP 側（v7 A〜E、v8 G/GT）

| 系列 | 調べたこと | 結果 |
|---|---|---|
| A | 色バッファと Z バッファの相対配置 | Z が色バッファの **±256KB 以内**にあると 64×8 矩形で +25〜33%、200 行リストで +3%。BAR（色 0x1DA800/0x200000, Z 0x3DA800）も DK64（色 0x1D240/0x42A40, Z 0x5D2E00）も「遠い」配置なので **原因ではない** |
| B | プリミティブ間の set/sync コマンド | set 系は 1〜6 clk で暗黙の待ちは無し。`set_convert`/`set_key_r` だけは sync 相当（≈400）で、以後 `Set_Other_Modes` まで遅い状態が残る（ゴミ値のため）。ゲームらしい並び: sync_pipe+set_other_modes ≈50（Z モード 15〜40）、sync_tile+set_tile ≈34、sync_load+image+tile+load_block 128B ≈100、F3DEX2 のテクスチャ切替一式 ≈155 — **モデルの値と一致** |
| C | 小プリミティブ間のテクスチャロード | ロードとプリミティブの干渉 ≈0 — モデルどおり |
| E/G/GT | プリミティブの配置 | 積み重ね（直前の続きの行に描く）以外の配置では、色/Z を読むモードで **スパンごとに +35〜50 clk**（散在矩形）、横並び h≥4 で 30〜41、三角形ストリップ 13〜26、散在三角形 28〜44。書くだけのモード（plain 1cyc）は 0、fill は +6〜11 |
| D | 他マスタの RDRAM 競合 | RDP の遅れは他マスタのトランザクション数に比例。約 2M trans/s で Z スパン ×1.19〜1.22、書くだけのスパン ×1.34〜1.39、copy ×1.3。SP DMA を全速で回すと ×9。VI 走査は Z モードのみ +6.9%、plain は 0% |

計測テーブル（積み重ね描画・アイドル機）と実ゲームの差は **「配置ペナルティ（スパンあたり）」と「競合係数（モード別）」**で
説明でき、旧版の「RDRAM 待ち部分 ×1.8」という自由パラメータは不要になりました。

### CPU 側（v8 F: RDP 描画中の CPU）

COP0 カウンタで CPU ループを計測（VI on、RDP に長いリストを描かせながら）。1 操作あたりの CPU サイクル:

| CPU 操作 | アイドル実機 | ares | RDP 描画中の増分（blend+Z / plain / fill） |
|---|---|---|---|
| dcache フィル（連続） | 38.8 | 45（48/40 設定） | +3.8 / +0.9 / +2.0 |
| dcache フィル（依存・ランダム） | 45.5〜46.6 | — | 計測不能（リストが先に終わる） |
| dcache ライトバック（copy から分離） | ≈41 | 40 | +10 / +26 / +15 |
| icache フィル（8 nop 込み） | 54 | ≈56 | +10 / +12 / +12 |
| 非キャッシュ読み 32bit | 41 | 11 | +3.6 / +0.6 / +1.3 |
| 非キャッシュ書き 32bit | 19 | 9 | +10.7 / +6.1 / +13 |
| ALU | 一致 | 一致 | 0 |

- RDP が描画中、CPU のキャッシュ転送は **icache +10、dcache +4、ライトバック +10〜25 サイクル**待たされます。
  旧版で「CPU ストール」を外した判断は、当時の値（一律 12〜20）が大きすぎたためで、計測値はその 1/3〜1/2 でした。
- ares の非キャッシュ RDRAM アクセスは実機より速い（読み 11 vs 40）ですが、両ゲームとも OP 中の非キャッシュ RDRAM
  アクセスは僅少（BAR 0、DK64 約 20 回/フレーム）で、MMIO アクセスも 100〜140 回/VI なので影響しません。

  重い場面のフレーム数（seg0）も 251→257（実機 225）と近づきました。
- DK64 は完走しますが、前半の CPU 律速区間（ブロック 4〜6）が実機より 10% ほど遅くなります（86〜87 → 91〜92、実機 82〜83）。

## 実機テスト ROM v9〜v16 と最終モデル（2026-10-31 更新）

v7/v8 までは合成プリミティブの計測でした。v9 以降は **ares からダンプしたゲームのディスプレイリスト（DK64 795〜797 /
1795〜1797、BAR 2316〜2318 / 2556〜2558、BAR intro 終盤・クラッシュ冒頭、MGC 2011）を実機で再生**し、ゲームと同じ
条件（VI モード、CPU/RSP のバス負荷）でリストあたりの RDP クロックを測りました。結果は `out/hw/` に保存してあります。

### RDP（v9/v10/v12/v15）
- **表モデルの精度**: vi_off で再生したリストに対し、表＋配置ペナルティ 15 の予測は DK64 ×0.96〜0.98、BAR intro ×1.00、
  BAR クラッシュ ×1.06〜1.08、BAR 終盤 ×0.99、MGC ×0.95〜0.98。コマンド種別を NOP に置き換えた variant（三角形のみ /
  ロードなし / 矩形なし / state のみ / フェッチのみ）の比率は **全リストで実機と ±3% で一致**し、残差はリスト単位の一様な
  スケールです（2 台の実機の vi_off 値は 0.1% 以内で一致）。
- **VI モード係数**（NTSC 本体、320×240 16bit、vi_off 比）: ROM の aa3（複製）×1.004、aa2（リサンプル）×1.03（1280 px 幅でも同じ）、
  **ゲームの AA0+divot+dedither ×1.117**、同 640 px 幅 ×1.324。PAL 本体は同じモードでそれぞれ ×1.020 / ×1.148 / ×1.179 / ×1.496 と
  明確に重く、本体（リージョン）依存です。モデルは NTSC 値を既定にしています。
- **バスマスターごとの競合**（RDP が失うクロック、ゲームの VI モード）: CPU D キャッシュフィル 14.6、命令フィル 12、ライトバック 6.2、
  非キャッシュ書き 5.5、SP DMA 64B 13.3 / 512B 91.5。ROM の VI モードでの値（11.7 / 8.5 / 5 / 3.7、DMA 1.22 clk/8B）に
  VI 係数で ×1.25（`viContendScale`）が掛かります。固定係数 1.13/1.19/1.07 は廃止し、転送ごとに `timingDelay` で課金。
- **コマンドフェッチ**: 352 KB のリストで 171k clk（フレームの 11%、2.8〜3.9 clk/word）。全体では描画と重なります。
- **DPC レジスタの意味（v13）**: `DPC_CURRENT` はフェッチポインタで、長いプリミティブ実行中は START+240（先読み 240 B）で止まる。
  実行中の `DPC_END` 延長は即時受理。実行中に新しい `DPC_START` を書くと次の END で切り替わるがその後 RDP がハングする
  （ゲームが避ける操作）。sync を外したリストも RDP をハングさせます（Set_Tile/Load が使用中のタイルに当たる既知の挙動）。

### CPU（v11/v14、NTSC/PAL 同値）
- 整数: ロード→次命令で使用 +1、ストア→次がメモリ命令 +1、D キャッシュヒット自体は +0（ares は +1 だった）、likely 分岐不成立も
  スロット分 1 cycle、mfc0 Count 2、mtc0 2、jr/beq はロード結果に対してインターロックしない。
- FPU はパイプライン: add/sub/mul（単・倍）発行 2 cycle、依存結果 3 cycle 後、cvt/trunc 5、div.s = sqrt.s = 28〜29、sqrt.d 30、
  比較 1。add/sub は桁落ちで 3 になる値依存あり。被除数 0.0 の div は早期終了（v11 の 15.5 はこれ）。
- バス: 非キャッシュ RDRAM 読み 33 cycle（ares 1〜2）、RCP レジスタ読み 23（MI は 11、DMEM/IMEM 29、RDRAM レジスタ 32）、PIF RAM 2981、
  カート ROM 219。書きは 4 エントリのライトバッファで 4 個までは 1 cycle、以降 ≈16/個（RCP は ≈9）、後ろの読みは排出待ち（未実装）。
- キャッシュ: クリーンフィル 41.4、dirty victim 付き 66（= fill + 25 のライトバック: ares は 80）、2 連続 fill 43/個。
  ares の RDP 描画中ストールは実測 fill +5 / 命令 +6 / wb +11、ゲームの VI モードでさらに +6 / +6 / +2。
- リコンパイラのバグ: スロウパス（ミス・非キャッシュ）を通る命令の 1 cycle が二重課金されていた（wScottSh の「インタプリタより +1」）。

### RSP（v16）
- **命令タイミングは ares と完全一致**（デュアル発行、依存ベクタ命令 4 cycle、lqv→使用 +1、分岐バブル、mfc0 2）。
- SP DMA は実機 38 RSP cycle + 0.155/B（out は 32 + 0.145/B）、ares は 1 系統クロック/8B だった → 114 系統クロック + 4/8B に。

- DK64 デモは実機に最も近い系列になりました（ブロック別の VI 数が 1〜2 以内）。

  残る差は CPU 側の数 %（値依存の FPU コスト、ライトバッファ、実測していない複合負荷での超加算）と考えられます。

  このデモは PI ロード・RSP・CPU が入り混じる別種の負荷で、RDP モデルの範囲外の要因が残ります。

## 実機テスト ROM v17〜v19 と v4 モデル（2026-10-31 追記）

v16 までは負荷を一つずつ測っていました。v17〜v19 は **負荷を同時に掛けたときの相互作用** と、v14 で測り残した
CPU の値依存コスト・ライトバッファを測りました（NTSC/PAL 各 1 台、結果は `hw/v17_*`, `v18_*`, `v19_*`）。

### v17: ゲームリスト再生 × CPU/RSP 複合負荷（8MB）
- **負荷は足し算**。単独負荷から求めた「RDP が失うクロック／操作」を回数で掛けた予測と、組み合わせ条件の実測の比は
  0.99〜1.03（ucw+dma64 のみ 1.06〜1.07）。CPU+RSP+VI+RDP が同時に走っても超加算は起きません。
- 操作あたり RDP が失うクロック（実機 / ares）: D キャッシュフィル 13.8 / 14.5（VI on）、9.7（VI off）、
  ロード+ストア混合（フィル 2 回＋書き戻し） 27〜28.5 / 34〜37.5、**非キャッシュ書き 4〜5（VI off 2.7）/ ares 0**、
  SP DMA 64B 11〜13 / 9〜17、512B 86 / 78〜81。→ 書き戻しの RDP ペナルティ `contendCpuW` 5 → 1、非キャッシュ書きに
  `contendCpuU` 4 を新設。
- CPU 側（RDP 描画中）: チェイス 1 フィル 55.5 cycle（ares 56）、混合 1 操作 130（ares 149 → 書き戻し直列課金のせい）、
  **非キャッシュ書き 33（ares 8.2）**。
- 注意: `icache` 負荷は 2 KiB の直線コードが I キャッシュ（16 KiB）に収まってしまい無負荷でした（結果は「CPU が
  キャッシュ内で回っているだけ」の対照条件として読めます）。また VI の効果が NTSC では 5 本目のリスト以降、PAL では最初から
  消えており（game と vi_off が同値）、v15 と同じ「VI が止まる」症状とみています。VI 込みの行は NTSC の最初の 4 リストだけ有効です。

### v18: FPU の値依存、ライトバッファ、書き戻しのドレイン、cache 命令
- **FPU（発行コスト、通常オペランド）**: add/sub（単・倍）3、mul.s 5、mul.d 8、div.s 29、**div.d 58**、sqrt.s 29、**sqrt.d 58**、
  cvt 5（cvt.d.s 1、cvt.s.d 2）、比較 1。依存する次の命令はさらに +1。高速パス: +0.0 の加算 2、×0.0 / ×1.0 / ×2.0 の乗算 2、
  被除数 0.0 の除算 2、sqrt(0.0) 2。v11/v14 で「add/mul 発行 2」「div.d 30」と見えたのは、オペランドが 1.0/0.0 で高速パスに
  入っていたためでした（sqrt.d 30 は 2 と 58 の平均）。ares 元来の値（add 5 以外）はほぼ正しかったことになります。
- **ライトバッファ**: 非キャッシュ RDRAM 書きは 1 エントリ 16.3 cycle（VI on 17.4）で排出、幅（sb/sh/sw）に依らず、sd は 18〜19。
  4 エントリまでは CPU は止まらず、5 個目から排出待ち。排出中に ALU 命令は進む（8 ストア×14 命令でも総時間は排出律速）。
  後続の非キャッシュ読みは排出完了まで待ち（+13）、**ラインフィルは排出完了 + 約 9 のバスターンアラウンド（+25）**、
  キャッシュヒットは待たない。SP/DP レジスタ書きは 10 cycle、MI レジスタ書きは 2。
- **ダーティ書き戻し**: 直後にフィルが来ると +28、間に 16 cycle 以上の作業があれば大半が隠れ、残差 +6。ares はこれまで 25 を
  直列に課金していました（v14 のテストが back-to-back だったため）。
- **cache 命令**: 1 命令 5 cycle（I-cache hit invalidate 6）、ダーティ行の書き戻しは 16 B で約 17 cycle（排出律速）、
  クリーン／不在行は 5 のみ。ares は 1 でした。

### v19: RDP 描画・VI・CPU ミス下の SP DMA（S 系列）
| 条件（RDP 待機/描画、VI、CPU） | dma_in 8B | 64B | 512B | 3584B |
|---|---|---|---|---|
| 待機 / off / idle（基準 38 / 44 / 108 / 581 RSP cycle） | 1.00 | 1.00 | 1.00 | 1.00 |
| 待機 / off / **CPU チェイス** | 1.16 | 1.39 | 1.74 | **1.94** |
| 待機 / **320×240 ゲームモード** / idle（PAL 本体） | 1.04 (1.12) | 1.10 (1.09) | 1.16 (1.24) | **1.18 (1.26)** |
| 待機 / ゲームモード / チェイス | 1.28 | 1.61 | 2.09 | **2.39** |
| fill / tex / texzb 描画中 / off / idle | 1.00〜1.12 | 1.05〜1.12 | 1.00〜1.06 | 1.01 |
- RDP の描画は SP DMA をほとんど遅らせません（+0〜5%、小さい DMA で最大 12%）。**CPU のラインフィルは DMA を大きく遅らせ**、
  3584 B の DMA に重なるフィル 1 回あたり約 18 RCP クロック、同時に CPU 側のフィルも 46 → 65 cycle（+19）。VI のゲームモードは
  DMA を 18%（PAL 本体 26%）遅くします。RSP の命令実行（vertex_like 37、mfc0 DPC_CURRENT 10）はどの負荷でも不変。
- D 系列（RDP リストの時間を SP DMA 連続下で測る）は v19 では ROM のバグで 0 行、修正版 **v19b** で取得（`hw/v19b_*`）。

### v19b D 系列: SP DMA 連続中の RDP
固定リスト（fill 40 矩形 ≈ 1.77M clk、tex 20 矩形 ≈ 1.63M clk）を、RSP が DMA を止めずに出し続ける中で計測（DPC_CLOCK は 24 bit で
一周するので CPU tick から換算）。**RDP は DMA 1 回あたり約 36 クロックしかバスを使えず、DMA のサイズに依りません**:

| DMA（連続） | イテレーション（RSP cycle） | RDP が使えた clk / イテレーション | RDP の遅れ |
|---|---|---|---|
| dma_in 8 B | 43 | 37 | ×1.2 |
| 64 B | 46 | 36 | ×1.3 |
| 512 B | 113 | 37 | ×3.1 |
| 3584 B | 585 | 36 | **×16** |
| dma_out 512 / 3584 B | 103 / 555 | 36 / 36 | ×2.8 / ×15 |
fill/tex、NTSC/PAL とも同じ。VI のゲームモードでは 33〜39、CPU チェイスが重なると約 30 に減る（チェイスは DMA 自体も伸ばすので
RDP への影響は条件により増減）。つまり RDP が失うのは「DMA の所要時間 − 約 32」= 1 転送 6 + 8 B あたり 1.2 クロック
（8 B: 6、64 B: 10、512 B: 76、3584 B: 549）。ares v4 は 8 B あたり 1.22 だけで転送ごとの分が無く、DMA 自体も 0.167/B と長めだった
ため、RDP に 55〜109 clk/イテレーション残り 3584 B で ×6 にしかなりませんでした。→ 0009 を v19b の規則に更新（DMA 0.15/B、
RDP ペナルティ 6 + 1.2/8B）。ゲームの DMA は疎（BAR intro: 682 回/VI、計 160 KB/VI、RDP 時間の約 3%）なので BAR は変わりません。

取りこぼし、(b) RDP リストの RSP 側（F3DEX2 の DMA が v19 のとおり CPU フィルで 1.4〜2 倍遅くなり、RDP への供給が途切れる：

## 実機テスト ROM v19b/v20 と v6 モデル：RSP が RDP を待つ（2026-10-31 追記）

### v20: ゲームの RSP グラフィックタスクをそのまま実機で再生
ares が BAR のグラフィックタスク起動の瞬間（SP_STATUS の HALT クリア）に RDRAM 4 MB・DMEM・IMEM・VI/DPC レジスタをダンプし、
0x80600000 にリンクした ROM がそれを実機に復元して RSP をゲームと同じ状態から起動、**RSP の停止（タスク完了）と RDP の DP 割り込み
（Sync_Full）の時刻を同時に**測りました（`hw/v20_*`、NTSC/PAL、各 3 回、min）。

| フレーム / 条件 | 実機 RSP 完了 [VI] | 実機 RDP 完了 | ares v5 RSP | ares v5 RDP |
|---|---|---|---|---|
| bar_2316 game idle | **1.538** | 1.587 | **0.504** | 1.484 |
| bar_2316 game chase | 2.285 | 2.378 | 0.532 | 2.421 |
| bar_2316 vi_off idle | 1.376 | 1.418 | 0.498 | 1.399 |
| bar_2579 game idle | 1.449 | 1.652 | 0.687 | 1.696 |
| bar_2520 game idle | 0.428 | 0.637 | 0.217 | 0.573 |

- **実機では RSP のタスクは RDP の 0.05〜0.3 VI 手前まで終わりません**。F3DEX2 は RDP コマンドを RDRAM 上の FIFO（この OSTask では
  0xFDF80〜0x100000 の 8 KB、フレームのコマンド 175 KB の 5%）に書き、次のフラッシュが RDP の未読部分を上書きしそうなら
  `DPC_CURRENT` を読んで待ち、FIFO の末尾では `DPC_CURRENT == DPC_END` を待ってから巻き戻します。ares は `DPC_END` を書いた瞬間に
  レンダラがコマンドを全部消費して `DPC_CURRENT = DPC_END` になるため、RSP は一度も待たず 0.5 VI で終わっていました（3 倍早い）。
  ゲームの CPU は SP 割り込み（タスク完了）を待ってから次のフレームへ進むので、ares は CPU を約 1 VI 早く解放していた——これが
  BAR intro の 2.0 vs 2.5 VI/フレームの機構です。
- RDP 側の時間は ares と実機で −6%〜+8% で一致（CPU チェイス下でも）。実タスクで RSP に供給される RDP は、同じコマンド列を連続リスト
  として再生した v15/v17（1.56M clk）より 6% 遅い（1.65M clk: FIFO が空く瞬間の待ちと RSP の DMA 競合）。
- PAL 本体は vi_off で NTSC と同値、VI ゲームモードでは +4%。

### v19b/v19c: SP DMA 連続中の RDP
RDP は DMA 1 回あたり約 36 クロックしかバスを使えない（サイズに依らない）→ 0009 の規則（1 転送 6 + 1.2/8B）は v5 で反映済み。

### 修正（パッチ 0010: `n64: DPC_CURRENT follows the modelled RDP progress`）
`DPC_END` の書き込みごとに「範囲（current..end）とそれが積んだ仕事量」を記録し、`DPC_CURRENT` の読み出しは **完了済みの仕事量が
届いている最古の未完了範囲の中の位置** を返します（範囲内は仕事量で線形補間、全部終われば END）。これだけで F3DEX2 の FIFO 待ちと
巻き戻し待ちが実機どおりに起き、v20 の ROM を ares で走らせると RSP 完了は RDP 完了の 0.05〜0.3 VI 手前になります（実機と同じ）。
セーブステートには範囲リングを入れていません（ロード直後は次の `DPC_END` 書き込みまで `DPC_CURRENT = DPC_END`）。

結果（クリーンコア 0001〜0010）: 下の結果表の series v6 行。BAR intro の seg0 はフレーム数 271 → 250 台（実機 225）に近づき、
60 VI ブロックごとのフレーム数のパターンが実機と同じ形（45 55 66 65 75 63 53 vs 実機 46 56 70 67 75 65 56）になりました。
残り約 10% は RDP モデルの -6%（VI ゲームモードの実タスク）と CPU 側の数 % の和とみています。

## ゲーム本体に常駐ロガーを入れた計測（bar_tasklog）と v15 のコマンド種別解析（2026-11-01 追記）

  235 / 39）。CPU 競合 10.8 だけでは DK64 27〜30、BAR 249〜254 で誤差内。**残差は内容依存の ±5% で、DK64 と BAR は反対側**にいます。

### v15 の「コマンド種別を NOP にした再生」で種別ごとに比較
v15/v15b（実機、VI オフ相当）の各リストについて、ares（v7、ハーネスで種別ごとの clk を集計）との差を種別に分けました
（`hw/v15_class_fit.txt`）。

| 種別（寄与 = full − no_X） | BAR 2316 系 | BAR 2556 / c2520（クラッシュ） | BAR t2500（軽） | DK64 797/1795〜7 | MGC |
|---|---|---|---|---|---|
| 全体 実機/ares | 0.99〜1.01 | **0.93〜0.95** | 1.01 | **1.02〜1.04** | 1.00〜1.03 |
| 三角形 | 0.99〜1.01 | 0.90〜0.93 | 1.03 | 1.02〜1.06 | 1.00〜1.07 |
| 矩形 | 1.03 | 1.01〜1.09 | 1.01 | 0.98〜1.02 | — |
| ロード | 1.01〜1.02 | 1.01〜1.07 | 1.02 | **1.06〜1.07** | 0.99 |
| Set 系のみ | 0.95〜0.96 | 0.96 | 0.96 | 0.95 | 0.93〜0.99 |

- BAR の三角形は **1 スパンあたり 5〜11 ピクセル**しかなく（2316: 7.8K スパン / 76K px）、コストの大半がスパンごとの固定分（テーブルの
  短スパン値 + spanPenalty 15）です。DK64 も同様（1CYC16_BLEND_ZPASS で 2〜3 px/スパン、88〜93 clk/スパン）。
- クラッシュ系リスト（2556/c2520）だけ三角形が 7〜10% 過大。これらは **Z テストで落ちるピクセル**の扱いの違いです: ares の推定器
  （Z ピクセル数 ÷ シザー面積から H(n)/n）は、Z 描画がシザーの半分しか覆わないため n≈1 → 通過率 1.0 を返していました。覆った画素を
  数える推定（ビットマスク、`T_ZCOVER`）にすると BAR の Z 描画は **40K 画素を 2.2〜2.5 回**、DK64 は 1.5〜1.66 回描いていると分かり、
  通過率は 0.68〜0.73 / 0.83〜0.88 になります。これでクラッシュ系は 0.93 → 0.97〜0.98 に改善しますが、**2316 系は 0.99 → 1.04〜1.06、DK64 は
  1.02〜1.04 → 1.05〜1.07 に悪化**します。つまり 2316 と DK64 の場面は奥→手前に描かれていて Z がほぼ全部通過し、クラッシュ場面だけ落ちている。
  描画順に依存するので推定では決まらず、**正しくはレンダラ（ソフトウェア RDP）の実際の Z 判定結果をプリミティブごとに時間モデルへ返す**必要が
  あります（parallel-rdp では取れないので、その場合は現在の推定にフォールバック）。これは今回の系列には入れていません。
- DK64 のロードは 6〜7% 低め、Set 系は全ゲームで 4〜5% 高め（どちらも全体の 1% 未満）。

### その他に確認したこと
- VI ゲームモードの係数（モデル 1.117 一律）は、v19b の実測で塗りつぶしリスト ×1.140（PAL 機 ×1.202）、テクスチャ矩形リスト ×1.101（×1.166）。
- RSP が RDP を待つ結合のコストは実機で +1.2〜1.4%（v20b: 通常 − 大 FIFO）ですが、ares では RDP が枯渇しないため 0。`DPC_CURRENT` の
  粒度（64 / 256 B に丸める）を試しても再現しません。
- 実機では intro が電源投入後 1114〜1134 VI で始まり、ares は 2412 VI（起動シーケンスの長さの違い。未調査）。

### 結論
BAR intro の残差（seg0 250 vs 230 フレーム）は、(1) ゲーム中の CPU 競合（+8%）、(2) RSP 供給の結合（+1.2%）、(3) 場面依存の Z 通過率
（クラッシュ場面で −7%）、(4) 軽いフレームでの内容依存誤差（+6.7%）の和で、いずれも ±数 % の項です。(1) と (2) は係数で入れられますが
DK64 を 1〜2 VI/ブロック悪化させる範囲にあり、(3) はレンダラ連携が要るので、series v7 のまま据え置きます。

### Q: DPC_CURRENT の進み方
bar_2316 を流しながら CPU が DPC_CURRENT を読み続けると（48.5K 回、1 ループ 22 tick = DPC_CURRENT + MI_INTR の読み出し 2 回）、
値の変化は 2210 回で、**1 回の進みは 128 B が 72%（1586 回）、64 B 13%、256 B 7%、≤32 B 8%**（最大 320 B、NTSC/PAL 同じ、VI の有無で同じ）。
RDP はコマンドを 128 B 単位で読み込み、DPC_CURRENT はその粒度で進みます。ares は 8 B 単位（ハーネスの `T_CURQ` で 64/256 を試しても
RDP 時間・BAR のフレーム数は変わらず）。副産物: 同じループが ares では 31 tick/回で、**RCP レジスタの CPU 読み出しが ares の方が 4 割遅い**
（ares は MI/DPC とも 22 cyc、実機は v14 で DPC 23・MI 11）。

### W: 垂直エッジの細い三角形（shade+texture+z、22 語、ランダム配置、4096 スパン）
`T(w, H) = 三角形固定分 + H × スパン単価` で H = 1,2,3,4,16 から分離（VI オフ、Z 全通過、clk）:

| | 三角形固定分 | スパン w=1 | w=2 | w=4 | w=8 | w=16 | w=32 | w=64 |
|---|---|---|---|---|---|---|---|---|
| 2cyc_tex_blend_z 実機 | **36〜51（平均 45）** | 74 | 78 | 85 | 97 | 121 | 167 | 237 |
| 同 ares v7（テーブル + 15 + prim_overhead） | −9〜+30 | 76 | 92 | 98 | 110 | 138 | 185 | 271 |
| 1cyc_tex_blend_z 実機 | **25〜49（平均 40）** | 74 | 81 | 85 | 97 | 118 | 154 | 223 |
| 同 ares v7 | −9〜+2 | 76 | 93 | 96 | 110 | 136 | 175 | 252 |

- 孤立した三角形には **約 45 clk の固定費**（22 語 = 176 B の読み出し ≈ 22 clk を含む）があり、ares の矩形由来の prim_overhead（−12〜+31）には無い。
  一方スパン単価は **テーブル値そのもの（+15 の spanPenalty は不要）**で、幅 32 以上では テーブルより 10〜20% 安い。
  1 スパン・1 px の三角形は実機 125.6 clk / ares 75.4（ares が 40% 安い）、w ≥ 16 では一致。
- Z: 全部落ちる（fail）と 1 スパンあたり **2cyc 29〜41 clk、1cyc 18〜49 clk 安く**、半分落ちる（half）はちょうど中間（例 2cyc H=3 w=8: pass 110.9 / half 93.3 / fail 75.3）。
  ares の「pass と fail のテーブルを通過率で線形に混ぜる」形は正しく、問題は通過率の推定だけです（v15 の結論どおり）。
- 他のモード（H=3）: 2cyc_tex（ブレンド・Z 無し）は w=2 で実機 91 / ares 57（固定費の欠落）、w=32 で一致。2cyc_tex_blend は ares が 10〜15% 高い。

### W の単価をそのままゲームのリストに当てはめると合わない
ハーネスに「三角形 +45、三角形のスパンは +3、幅 16 超は 1 px あたり −0.8」（`T_TRIOV=45 T_TRISP=3 T_SPWIDE=0.8`）を入れると W 系列は ±5% で
合いますが、V 系列の三角形は **実機/モデル = 軽 1.19〜1.21、重 1.05〜1.10、bar_2316 1.13、DK64 1.06** と、ゲームの三角形の方が
同じ幅・高さの合成三角形より 1〜2 割高くつきます。v9 で入れた spanPenalty 15 は、この差を経験的に吸収していたものです。

ゲームの三角形と W の三角形の違いを洗うと、まず **ラスタライザの画素数の数え方**が見つかりました。ares の時間モデルは行中心でエッジを評価して
`x1 − x0` 画素としますが、実機（angrylion のエッジウォーカー）は 4 サブスキャンラインの左端の floor から右端の floor まで**両端を含めて**処理し、
行もサブスキャンラインが 1 本でも入れば描きます。これをハーネスに入れる（`T_RASTER=1`）と、ゲームのリストのスパン数が BAR で +6〜11%、
DK64 で +17%、画素数が +6〜14% 増え、W の単価と合わせた結果は 重いフレーム 1.01〜1.02、bar_2316 1.04、軽いフレーム 1.06〜1.10、
bar_i2404/2410 0.94、DK64 0.85 になります。残りは Z 通過率（bar_i2404/2410 と DK64 は推定より落ちている可能性）とモードビット
（AA、パースペクティブ、LOD、ディザ、TLUT など W の三角形に無いもの）のどちらかで、これを切り分けるのが v23 です。

## 修正内容（パッチ 0001〜0012、ハーネス 9999）

（`0001` は独立したバグ修正: `ares/n64/rdp/io.cpp` `RDP::readWord` の DPC_TMEM_BUSY 判定が `if(data == 7)` になっていて

`0002`（RDP モデル）の変更ファイル: `ares/n64/rdp/timing.cpp`(新規), `ares/n64/rdp/timing-model.hpp`(新規・実機計測テーブル),
`rdp.hpp`, `rdp.cpp`, `render.cpp`, `io.cpp`, `serialization.cpp`, `vulkan/vulkan.cpp`, `system/serialization.cpp`(ステート版数 v154),
`n64/CMakeLists.txt`。`0003`（CPU ストール）の変更ファイル: `ares/n64/cpu/cpu.hpp`, `cpu.cpp`, `dcache.cpp`, `recompiler.cpp`。
いずれも上流 master（a774671d, 2026-10-26 時点）にそのまま適用できることを確認済みです（0001〜0012 は `git am`、9999 は `git apply --check` で確認）。
`0012` は v24/v25/v28 の節のモデル（Z の全滅はスパン 16 px 以下だけ、ATOMIC_PRIM 20 clk/プリミティブ、1 サイクルの AA 3.5 clk/スパン、
`rdp.hpp` の `zFailWidth` / `atomicCost` / `aaSpanCost`）、`9999` が検証ハーネスです（毎回番号が変わらないよう固定番号にしています）。
`0007` は MGC 2011 デモのエミュレータ検出を通す PI タイミング修正（`n64: make cartridge ROM ignore PI accesses faster than a mask ROM can serve`、`cartridge.hpp` と `pi/device.hpp`）、`0008`/`0009` は上の v17〜v19 節、`0010` は v20 節、`0011` は v20b 節のモデルです。

1. **RDP 実行時間モデル** (`timing.cpp` + `timing-model.hpp`)
   - parallel-rdp 経路・ソフトウェア経路の両方で、レンダラに渡すのと同じコマンド列を解析。
   - コマンドごとのサイクル数は **実機計測モデル（rdp_timing v3〜v6、NTSC/PAL、`DPC_CLOCK` 読み取り）** の
     テーブルをそのまま使用（`rdp_timing_model.h` を `timing-model.hpp` として同梱）:
     - 三角形／矩形: `prim_overhead(mode, 最大幅)`（＋シェード/テクスチャ付き三角形は +3）と、スキャンラインごとの
       `span(mode, 先頭画素のRDRAMアドレス, 幅)`。三角形のスパンはエッジ係数から行ごとに求め（シザー適用）、
       アドレスは Set_Color_Image のアドレス・幅・深度から計算（64バイトブロック内位相が効く）。
     - モード: サイクルタイプ×色深度×imageRead×zCompare/zUpdate から 26 モードのテーブル行を選択。
       4/8bpp 色バッファと 32bpp コピーは計測が無いため 16bpp テーブルをバイト数換算で流用。
     - Z テスト: テーブルは「全画素パス」「全画素フェイル」の 2 系統なので、パス率で補間。
       パス率は **前フレームのオーバードロー**（Zテスト画素数 ÷ シザー面積 = n）から H(n)/n
       （ランダム順で n 層描くとき k 層目がパスする確率 1/k の総和）で推定（1層=1.0、2層=0.75、3層≈0.6）。
       0012 以降、この推定は **幅 16 px 以下のスパンだけ**に適用（実機では画素単位の部分的な Z フェイルは何も節約せず、
       スパン丸ごと隠れたときだけ安くなる: v24/v28）。
       compare のみ／update のみは 16bpp 1-cycle の計測行を同幅の zpass 比でスケール。
     - Load_Block / Load_Tile（行ごとの RDRAM アドレスから 8B ワード数・64B ブロック数）/ Load_TLUT、
       Sync_Pipe/Tile/Load 50/33/25、その他の set 系 2.62（DMEM からのリストは 1.73）、
       Sync_Full ごとにリスト基本コスト 93。
   - テーブルは「積み重ね描画・CPU/RSP ほぼ停止」の計測なので、実機で計測した 3 つの補正を掛けます（前節）:
     色/Z を読むスパンは `spanPenalty`(40) を加算し `contentionZ`(1.13)、VI 走査中はさらに `viFactor`(1.07) を乗算、
     書くだけのスパンと TMEM ロードは `contentionPlain`(1.19) を乗算。
2. **RDP スレッドが仕事を消費**: `RDP::main()` が保留中の仕事をクロック進行に合わせて消費（FREEZE中は停止）。
   Sync_Full はキューに入り、その時点までの仕事が完了した時点で DP 割り込みを発生、busy フラグをクリア。
3. セーブステートに状態を追加し版数を v154 に更新。
4. **CPU ストール**（`0003`）: RDP モデルに未消化の仕事があり FREEZE 中でない間、CPU の icache フィルに +10、
   dcache フィルに +4、dcache ライトバックに +12 サイクルを加算（`CPU::rdpBusyStall`）。リコンパイラがインライン展開する
   icache フィル経路には `CPU::icacheStall()` の呼び出しを追加。RDP モデルを無効にすると CPU 側も従来どおりになります。

## 注意点・残課題

- （2026-11-01 追記、現状の総括）**DK64 のデモは series v7/v8 で実機と 1〜2% 以内**（dk64_tasklog: RDP 律速フレーム −1%、CPU 律速フレーム +2%、
  合計 +0.8%、PI DMA の速度も同じ）。**BAR intro は seg0 249 vs 230 フレーム（ares が 8% 速い）のまま**で、その残りは
  (1) ゲーム中だけ乗る分（RSP DMA 競合・FIFO 結合・CPU 競合、合わせて +2〜4%）と、(2) **三角形の単価の「場面の中身」依存の ±10〜15%**
  （v28: 重なり方・描画順で決まり、幅・モード・テクスチャ・配置・コマンドでは説明できない。BAR の重いフレームと DK64 では打ち消し合い、
  BAR の軽いフレームでは同じ向きに積む）です。(2) をテーブルで詰めることはできず、ピクセル単位の RDP シミュレーション（angrylion 相当の
  メモリアクセスモデル）が要ります。一律の係数・実機のエッジウォーカーなど BAR を合わせる変更はいずれも DK64 を壊します（v24 候補表）。
- （2026-10-31 追記）BAR intro: 機構は v20 で確定（RSP が FIFO で RDP を待つ → パッチ 0010）。v20b でフレーム 2316 の RSP+RDP は
  実機 1.587 VI に対し ares 1.553（−2%、v6 は −3.4%）まで詰まりましたが、intro 全体は 249 vs 225 フレーム（+11%）のまま。1 フレーム分の
  RSP/RDP 時間の差（0.03〜0.08 VI）では説明できない量で、残りは **CPU 側（ゲームロジック）か、フレームごとの RSP タスク（音声タスクによる
  yield を含む）の並び**にあります。次は実機で「CPU がフレームごとに何 VI 使っているか」（SP 割り込みから次のタスク起動までの時間）を
  測る ROM か、BAR の CPU 処理そのものをダンプして再生する ROM が要ります。
- v20b で 2 台の本体の差が見えました: VI ゲームモード下で RSP の DMA が RDP から奪う時間が NTSC 機 71 clk/DMA、PAL 機 47（VI オフは両機 51）、
  RDP 単独の VI 係数も NTSC +11.3% / PAL +18.6%。モデルは NTSC 機寄り（係数 ×1.28、+11.7%）です。
- `tex`（テクスチャロードを含むリスト）＋ VI ゲームモード＋ CPU ミス＋ 3.5 KB SP DMA 連続は実機の RDP が止まる（両機で再現、v19c）。
- VI 係数は NTSC 本体の値。PAL 本体は同じモードで 5〜15% 重かったので、PAL 版 ROM を PAL 機で合わせるなら `viFactor*` の PAL 用の値が要ります。
- RCP レジスタ読みは一律 23（MI だけ 11）、非キャッシュ RDRAM 読みは 32。FPU の高速パス（0.0 / 1.0 / 2^n オペランド）はモデル化していません（通常値を課金）。
- VI 係数は NTSC 本体の値（PAL 本体は VI の影響が 5〜26% 大きい: v15/v19）。

- 較正はこのデモ（ジャペス）の実機録画 1 場面に基づきます。他の場面・他タイトルで同じ係数が最適とは限りません。
  同様の 60fps 録画があれば `analyze.py`（録画→表示間隔列）と `score.py`（ares ログとのブロック比較）で同じ手順で検証できます。
- RDP 時間が 0 → 現実的な値になるため、**他タイトルのフレームレートに影響が出る可能性**があります
  （特に RDP 負荷が高い 60fps タイトル）。手元にはこの ROM しかないため他タイトルは未検証です。
  問題が出た場合は `rdp.hpp` の `Timing` 構造体の `spanPenalty`/`contentionZ`/`contentionPlain`、`cpu.hpp` の
  `*Stall` 定数を調整してください（いずれも実機計測値で、自由パラメータは残していません）。
- 本環境では Vulkan（parallel-rdp）が初期化できず（SwiftShader が 16bit ストレージ非対応）、
  画面での目視確認はできていません。検証は RAM 上の座標・状態遷移（ロープ区間の Y 振動、大砲射出、次デモへのマップ遷移）で行いました。
- US/PAL 版でも同じ仕組み（アドレスは異なる）のはずですが、未検証です。PAL は 50Hz のためデルタの閾値（20ms）が異なり、
  較正の当たり方が変わる可能性があります。
