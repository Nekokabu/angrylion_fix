# bar_tasklog — ビートルアドベンチャーレーシング (J) の実機フレームタイムライン記録

ゲームそのものに常駐ロガーを入れたパッチです。ゲームの libultra の 4 関数をフックして、COP0 Count 付きで

- `osSpTaskLoad`（タスク種別 1=グラフィック 2=音声、フラグ: bit0 = yield からの再開）
- `osSpTaskStartGo`（SP_STATUS の HALT クリア = RSP 起動の瞬間）
- 例外ハンドラの `send_mesg`（SP / DP / VI / AI / SI / PI 割り込みイベント。SP は SP_STATUS の halt/broke/sig0〜2、DP は DPC_STATUS、VI は走査線/2 を添付）
- `osSpTaskYield`（音声タスクのためのグラフィックタスク中断要求）

を 4 バイト/件で記録します（上位 16 bit = 前の記録からの Count 差/16、1 VI = 781250 Count）。記録は **intro の最初の重いフレーム（0.5 VI 以上のグラフィックタスク）の完了**で始まり、
**32 KB（約 8000 件、intro 全体の約 1600 VI）** が溜まるとカートリッジの **SRAM（0x08000000）に書いて停止**します（画面が止まったら完了。intro 開始から約 27 秒後）。ゲームの CPU 時間がフレームごとに「RSP 起動 → RSP 完了 → 次の RSP 起動」として得られ、ares で同じ
パッチ ROM を走らせたログと直接比べられます。

## 必要なもの

- ビートルアドベンチャーレーシング (J) の ROM（16 MB、.z64/.n64/.v64 いずれも可）— **ROM 自体は同梱していません**。お手元のダンプから作ります。
- **拡張パック（8 MB）の本体**。ロガーは上位 4 MB（0x80700000〜）に常駐します（ゲームは上位 4 MB を使いません）。
- EverDrive 64 X シリーズ。セーブタイプを **SRAM 256K** に手動設定してください（このゲームは本来セーブ無しなので自動では選ばれません。768K でも可）。

## 手順

1. パッチ ROM を作る（Python 3）:
   ```
   python3 make_patch.py <BAR_J.z64> hook.bin bar_tasklog.z64
   ```
   ゲームコード NB8J とフック位置の命令を確認し、エントリ 52 バイトの差し替え、ROM 末尾のパディング領域（0xFF0000〜）へのロガー書き込み（ROM サイズは 16 MB のまま）、CIC チェックサム再計算を行います。
2. SD に入れて EverDrive で起動（セーブタイプ: SRAM 256K）。そのまま放置。タイトル → EA ロゴ → intro（クラッシュのデモ）が流れ、
   **intro 開始から約 27 秒で画面が止まります**（書き込み完了）。コントローラは触らなくて構いません（触っても記録には影響しません）。
3. リセットして EverDrive のメニューに戻り、セーブデータを SD に書かせます（`bar_tasklog.srm`、32 KB）。そのファイルを送ってください。
4. 解析: `python3 decode_tasklog.py bar_tasklog.srm`（`--events` で全イベント、`--csv out.csv` で表）。

## ares 側の参照

`ares_v7.srm` は同じパッチ ROM を ares（series v7）で走らせたログ、`ares_v7_frames.txt` がその解析結果です。intro の 1 フレーム（RSP 起動 → 次の RSP 起動）は
常に 2.00 または 3.01 VI（VI 同期）で、RSP 完了 1.05〜1.83 VI、完了から次の起動までの CPU 側の余り 0.23〜1.3 VI になっています。実機のログで
「RSP 完了が何 VI か」「次の起動までの余りがどれだけか」を比べれば、残差が RSP/RDP 側か CPU 側かが決まります。

## 中身

- `hook.S` — 常駐ロガー（MIPS アセンブリ、libdragon の mips64-elf-gcc でビルド）、`hook.bin` — そのバイナリ（約 1.2 KB、ROM 内 4 KB 枠）
- `make_patch.py` — パッチ生成（エントリ差し替え: ROM 0xFF0000 のブロブを CPU の非キャッシュ読み書きで 0x80700000 に複写してジャンプ。ブロブの init が元のエントリの処理（bss クリア、sp）と
  フックの書き込み（RAM 上の命令を `j`/`jal` に差し替え、キャッシュ操作）を行う）
- `decode_tasklog.py` — ログの解析（EverDrive の .srm、または エミュレータの RAM ダンプから切り出した 96 KB）

## v2 → v3（2026-10-31）

- v2: ROM サイズを 16 MB のまま（ロガーは末尾パディング 0xFF0000）、エントリの PI DMA を CPU 複写に変更 → 実機で起動するようになりました。
- v2 の実機ログ（SRAM 768K 設定）は **先頭 32 KB だけが有効**でした（EverDrive の SRAM は 32 KB で折り返し）。そこで v3 では
  - 記録開始を「VI 番号」ではなく **「0.5 VI 以上かかったグラフィックタスクの完了」（= intro の最初のフレーム）** に変えて、実機と ares で同じ位置から記録、
  - PI/AI/SI イベントと音声タスクの load/go を記録せず（SP イベントの extra バイトの bit5..6 に直前にロードしたタスク種別を入れる）、
  - バッファを 32 KB にして一杯になったら書き込み（intro 開始から約 1600 VI = intro 全体）。セーブタイプは **SRAM 256K で十分**です。
  - トリガが掛からなかった場合も 7000 VI で書き込んで停止します。
- 画面が止まるのは intro 開始から約 27 秒後です。

**拡張パック（8 MB）が無い本体では必ず黒画面になります**（ロガーの複写先が存在しないため）。

## v4（2026-10-31）: CPU を止めて RDP だけを測る変種

`hook_idle.bin` で作った ROM（`python3 make_patch.py <ROM> hook_idle.bin bar_tasklog_idle.z64`）は、記録中、グラフィックタスクを起動した CPU が
**RSP が止まるまで SP_STATUS を読むだけのループで待ちます**（RDRAM に触らない）。スケジューラスレッドが止まるので音声タスクによる yield も起きず、
グラフィックタスクは一気に最後まで走ります（intro 中は音が途切れます。想定内です）。これで「ゲーム中の CPU の競合が無いときの RSP/RDP 時間」が
取れ、通常版との差がゲーム中の CPU 競合の実測値になります。手順・セーブタイプは同じ、画面が止まるまでの時間は少し長くなります（約 40 秒）。

ares（v7）では通常版と idle 版の差（= モデル上の CPU 競合）が重いフレームで 0.14〜0.41 VI、実機の通常版は ares の idle 版より 0.2〜0.55 VI 遅いので、
実機の idle 版が ares の idle 版と同程度なら「ゲーム中の CPU 競合がモデルより 3 割ほど大きい」ことが確定します。
`ares_v7_idle.srm` / `ares_v7_idle_frames.txt` が ares 側の idle 版ログです。

### v4b: idle 版の修正
実機では SP_STATUS への書き込みが反映されるまでに少し時間があり、直後に読んだ HALT がまだ 1 のためループが即座に抜けていました（idle 版の実機ログは
通常版と同一の結果 = 再現性の確認にはなりました）。v4b では「HALT が 0 になるのを待ってから、再び 1 になるのを待つ」に直しています。

### v4c: idle 版の識別と待ち方の変更
実機で 2 回とも通常版と同一の結果（yield も起きている）だったため、idle 版が本当に走ったか判別できるようにしました:
ヘッダの version が **4**（通常版は 3）、待ち終了時に kind 5 のエントリ（`--events` で "CPU idle wait ended"）が入ります。待ち方は
「Count で 0.01 VI 待ってから HALT が立つまで待つ」に変更。**出力 ROM のファイル名を通常版と変えてください**（例 `bar_tasklog_idle.z64`。
EverDrive のセーブファイル名も ROM 名になります）。
